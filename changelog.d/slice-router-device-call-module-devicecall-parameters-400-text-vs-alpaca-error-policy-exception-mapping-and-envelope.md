### Changed

- **Device calls read their parameters, build the response and decide 400 versus an Alpaca error in one place** (AlpacaHTTP, issue #1612): the new `DeviceCall` (`device_call.cpp`) replaces the per-dispatcher parse lambdas, the eleven catch blocks and the transaction-id copies in `router.cpp`, so a request body is parsed once instead of once per parameter read (`test_device_call.cpp`, `case_body_parsed_once`). A missing or unparsable parameter is still HTTP 400 text and a refused or failed operation still HTTP 200 with an Alpaca error number (`case_run_bad_request_is_400_text`, `case_run_invalid_value_stays_200`).
- **The telescope accepts a JSON or form `Value` field for its double and integer parameters**, as every other device type already did: `{"Value": 2.5}` now sets `GuideRateRightAscension` where it was answered with HTTP 400 `Missing parameter` (`case_json_value_fallback`, `case_form_value_fallback`).
- **An exception that is not an `AlpacaException` is always reported as `DriverError` (0x500) with its own text**: the guess from words in the message ("not connected", "invalid value", ...) is removed, as no in-tree code reached it (`case_run_std_exception_is_driver_error`).
