### Breaking changes
- **Telescope optics and SlewSettleTime answer NotConnected while disconnected** (AlpacaCore; Bisque, Celestron NexStar, iOptron, OnStep, Sky-Watcher, SynScan and ZWO telescope drivers): `ApertureDiameter`, `ApertureArea`, `FocalLength` and `SlewSettleTime`, and a `SlewSettleTime` write, now answer `NotConnected` (0x407) while the mount is disconnected, while a connect is in progress and after the link is lost. Before, they answered the configured value, and the write stored the new value. A negative `SlewSettleTime` write still answers `InvalidValue` (0x401) first. The web UI and the saved config are not affected: the device page still shows the optics, and a web UI edit of the optics still applies while the mount is disconnected. **After upgrading:** a client that read these properties before `Connected = true` must connect first, or handle `NotConnected`.

### Fixed
- **Telescope optics and SlewSettleTime follow the ASCOM connection check** (AlpacaCore; Bisque, Celestron NexStar, iOptron, OnStep, Sky-Watcher, SynScan and ZWO telescope drivers): these members answered while disconnected, against the ASCOM rule that every member except parameter validation throws `NotConnected` first. All eight telescope drivers now do what the Celestron CGX driver already did. The check takes no lock held during device I/O. While connected, a latched link fault does not refuse these members, because they are the user's own values. The Sky-Watcher `SlewSettleTime` write and the ZWO synchronous slew's settle wait now use the value under the driver mutex. For clients, see Breaking changes.
- **SynScan: the next RA stop restores tracking after a failed tracking restore** (AlpacaCore, SynScan telescope driver): when the `T` command that resumes tracking after an RA move timed out, the next RA `PulseGuide`, `MoveAxis(0, ...)` stop or `AbortSlew` read the handset's mode 0 (the RA rate command had replaced tracking) and used it as the mode to restore. The mount stayed untracked although the client had set `Tracking = true`, and the next RA pulse ran at the guide rate alone. These stops now send the mode the client asked for. A `Tracking` write that fails in this state still records its mode, so a failed `Tracking = false` does not turn tracking back on at the next stop. `Tracking` still reads false, and slews are still refused, until a restore lands. A keypad change of the tracking mode made in this state is not seen.

### Added (tests)
- **Telescope optics in the contract sweep, and SynScan failed-restore cases**: the telescope `NotConnected` probes in `AlpacaCore/tests/test_contract_sweep.cpp` now include the four optics and settle-time getters and the `SlewSettleTime` write, and the `InvalidValue` probes include `SlewSettleTime(-1)`, for all eight telescope entries. Three new cases in `AlpacaCore/tests/test_synscan_async_slew_failure.cpp` cover an RA pulse, AbortSlew, MoveAxis and a failed `Tracking = false` after a failed restore. The `ra_move_keeps_tracking` knob is removed from the shared fake SynScan handset, so an RA variable-rate move always replaces tracking, as on the handset.
