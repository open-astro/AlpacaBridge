### Fixed

- **OnStep: a faulted `DeviceState` no longer stalls for many reply timeouts** (issue #1626): while the link fault was latched, each getter waited out the reply timeout under the driver's lock, so a `DeviceState` (about eight getters) took about eight timeouts and blocked every other call. For 2 s after a read that failed while faulted, the reads now throw the fault without asking the mount; then one read asks again, and a reply clears the fault as before. Test: `test_onstep_link_loss.cpp` "OnStep link loss - a faulted DeviceState asks the mount at most once in the back-off".
- **OnStep: site and `UTCDate` writes are refused while the link is faulted** (issue #1626): they went to a mount that was not answering and reported success. They now throw the fault, like the motion and state commands. Test: `test_onstep_link_loss.cpp` "OnStep link loss - a mount that stops answering latches a fault and a reply clears it".
- **OnStep: a read that finds the link lost reports it even while a cache is valid** (issue #1626): it served the cache once more. Test: `test_onstep_link_loss.cpp` "OnStep link loss - a lost link during the failed reads is not latched as a fault".
- **OnStep: `UTCDate` read from the mount used the UTC offset backwards** (issue #1626): OnStepX's `:GG#` is the hours to add to local time to get UTC, and the driver subtracted it, so a mount whose time zone was set elsewhere (a handset or app, e.g. +05 for EST) reported a `UTCDate` 10 hours off with no error. AlpacaBridge itself writes offset 0, so a mount it set was not affected. A date or offset reply that does not parse now fails the read instead of storing 2000-01-01. Test: `test_onstep_telescope.cpp` "OnStep Telescope Driver - UTCDate throws InvalidOperation when the mount clock cannot be read".
