### Breaking changes

- **A missing or unparsable Device API parameter now answers HTTP 400 text, and Device API 400 bodies are plain text** (AlpacaHTTP router, issue #1476). A required parameter that is missing, or whose value does not parse as the required type (`Position=abc`, `TempComp=maybe`, a JSON field of the wrong type, a non-whole or out-of-`int` integer, a `nan` or hex-float number), used to answer HTTP 200 with `InvalidValue` (0x401). It now answers HTTP 400 with a short `text/plain` message naming the parameter (Alpaca API Reference s2.5), and never reaches the driver. The `FocusOffsets` elements of a filter wheel `focusoffsets` `PUT` (an AlpacaBridge extension) follow the same rule as every other JSON integer parameter: `[0.5]`, `[4294967296]` or `["x"]` answer HTTP 400, and a numeric string element such as `["5"]` is now accepted as 5 where it used to answer `ErrorNumber` 0x500. A `sensordescription` or `timesincelastupdate` request with no sensor name now names the `SensorName` parameter in its message instead of `PropertyName`. A value that parses but is out of range for the device stays HTTP 200 with `InvalidValue`. Every other Device API 400 (unknown device type, invalid device number, unknown method, wrong verb, unregistered device, and the over-long path on every path) also carries `text/plain` instead of the JSON envelope; the 400s of `PUT`/`POST` `/management/v1/description`, `configuredevice` and `update/channel` keep the JSON envelope. **After upgrading:** a client that sent a missing or malformed parameter and read `ErrorNumber` 0x401 from a 200 now reads HTTP 400 and its text, and a client that parsed a Device API 400 body as JSON reads plain text. Covered by `AlpacaHTTP/tests/test_routing.cpp` (the missing/unparsable cases, the Device API 400 sites, the description write staying JSON) and `AlpacaHTTP/tests/test_route_table.cpp`.

### Fixed

- **Out-of-range integers in management requests are refused, not wrapped** (AlpacaHTTP router, issue #1476). `PUT /management/v1/wifi/profiles` with a `Priority` outside `int` and `PUT /management/v1/wifi/ap` with a `Channel` outside 32 bits used to wrap the value (`4294967296` became `0`) and pass it to NetworkManager; they now answer an error naming the field. A `deviceNumber` outside `int` or with a fraction in `configuredevice` or `removedevice` used to address another device (`4294967299` became device 3, `3.5` became 3); it now answers `InvalidValue` naming `deviceNumber`, and a persisted entry with such a number is listed as failed with `DeviceNumber` -1. A wrong-typed config field in those two requests is now logged at DEBUG instead of ERROR. Covered by `AlpacaHTTP/tests/test_routing.cpp` (the Wi-Fi body validation rows and the `deviceNumber` cases).
