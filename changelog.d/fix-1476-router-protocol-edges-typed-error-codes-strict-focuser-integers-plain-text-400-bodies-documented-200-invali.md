### Breaking changes

- **A missing or unparsable Device API parameter now answers HTTP 400 text, and Device API 400 bodies are plain text** (AlpacaHTTP router, issue #1476). A required parameter that is missing, or whose value does not parse as the required type (`Position=abc`, `TempComp=maybe`, a JSON field of the wrong type, a non-whole or out-of-`int` integer, a `nan` or hex-float number), used to answer HTTP 200 with `InvalidValue` (0x401). It now answers HTTP 400 with a short `text/plain` message naming the parameter (Alpaca API Reference s2.5), and never reaches the driver. A value that parses but is out of range for the device stays HTTP 200 with `InvalidValue`. Every other Device API 400 (unknown device type, invalid device number, unknown method, wrong verb, unregistered device, and the over-long path on every path) also carries `text/plain` instead of the JSON envelope; the 400s of `PUT`/`POST` `/management/v1/description`, `configuredevice` and `update/channel` keep the JSON envelope. This replaces the `InvalidValue` answer for a JSON-body integer that is not a whole `int` described in an earlier entry. **After upgrading:** a client that sent a missing or malformed parameter and read `ErrorNumber` 0x401 from a 200 now reads HTTP 400 and its text, and a client that parsed a Device API 400 body as JSON reads plain text. Covered by `AlpacaHTTP/tests/test_routing.cpp` (the missing/unparsable cases, the Device API 400 sites, the description write staying JSON) and `AlpacaHTTP/tests/test_route_table.cpp`.
