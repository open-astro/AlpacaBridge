### Breaking changes
- **SynScan: Tracking=true now refuses AZ-EQ mounts and equatorial mounts with no site latitude** (AlpacaCore, issue #774; `synscan_telescope_driver.cpp`): 4.2.0 always sent equatorial tracking mode 2. Now an AZ-EQ5 or AZ-EQ6 (handset model ID 5 or 6), or any model ID the driver does not know, gets `DriverException` ("SynScan cannot report whether this AZ-EQ mount is currently configured for Alt-Az or equatorial alignment", or "cannot determine AlignmentMode for mount model ID N") from both `Tracking=true` and `AlignmentMode` while the device's Alignment Mode setting is `auto` (the default, issue #860). An equatorial mount with no site latitude, from the handset or the config, gets `ValueNotSet` ("Set SiteLatitude before enabling equatorial tracking"). **After upgrading:** set the site latitude in your client or the web UI; an AZ-EQ5 or AZ-EQ6 owner who needs tracking sets the device's Alignment Mode to Alt-Az (`altaz`) or Equatorial (`equatorial`) in the web UI to match how the mount is set up.
- **Saved GPIO switch configs with non-board values no longer load** (AlpacaHTTP, issues #765 and #818; `router.cpp`): the new hardware-config checks also run on the saved devices read at startup, so an entry 4.2.0 accepted is skipped with "Skipping persisted device: Hardware config refused: ..." in the log and is missing from the device list. It affects a ZWO ASIAIR switch with a `ports[].gpio` other than 12, 13, 26 or 18, a repeated line, or a `gpioChip` other than `/dev/gpiochip0`; an ASIAIR Plus whose `devicePath` is not `/dev/pwm-gpio-misc`; an iOptron iMate PowerBox whose `gpioChip` is not `/dev/gpiochip1` or `/dev/gpiochip0`; and a ToupTek StellaVita PowerBox whose `gpioChip` is not `/dev/gpiochip0`. `configuredevice` refuses the same values with HTTP 400. **After upgrading:** add the device again in the web UI, whose form now offers only the board's values.
- **Saved catalog devices with a fractional number or a boolean in a whole-number field no longer load** (AlpacaCore and AlpacaHTTP, device catalog): the vendors moved into the device catalog in this release type their whole-number fields strictly, so a saved value such as `9600.5` or `true` that 4.2.0 truncated to an integer is now refused, and the device is listed as failed to load. The fields: Sky-Watcher direct `baudRate`, `udpPort`, `mountIndex` and `responseTimeoutMs`; WeeWX `pollIntervalSeconds` and `timeoutMs`; SVBONY and Canon/Nikon (gphoto) `cameraIndex`; Player One `cameraIndex` and `filterwheelIndex`; Bisque `tcpPort` and `responseTimeoutMs`. `configuredevice` refuses the same values. **After upgrading:** re-save the device with a whole number (a float with no fractional part, such as `9600.0`, is still accepted).
- **iOptron: a GOTO the mount refuses now fails instead of being retried with relaxed limits** (AlpacaCore, issue #763; `ioptron_telescope_driver.cpp`): 4.2.0 answered a refused GOTO by writing an altitude limit of -89 degrees (`:SAL-89#`) and the meridian treatment `:SMT130#` and retrying, so a target below the mount's own altitude limit or past its meridian setting could still be reached. The driver no longer changes either setting, so that GOTO now ends with an error (a `Slewing` error for an asynchronous slew). **After upgrading:** if a target you used to reach is refused, change the altitude limit or meridian setting on the mount (hand controller or iOptron Commander) yourself.

### Changed (docs)
- **Changelog categories corrected for the changes since 4.2.0, and a test for what counts as breaking** (docs, `changelog.d/README.md`, `AGENTS.md`, `.claude/commands/commit.md`, `.claude/commands/submit-pr.md`): a review of every commit since 4.2.0 found four changes that break a 4.2.0 setup filed under `Changed` or `Fixed` only; they now have the `Breaking changes` entries above, so the next release is a major version. Three entries written straight into `CHANGELOG.md` on 2026-09-30, after the 4.2.0 tag, sat in the released 4.2.0 section (the Bisque handshake timeout fix, the ZWO GOTO-setup fence and WeeWX joining the device catalog) and move to this release's section, where their code ships. The Host allowlist entry no longer says router DNS names get HTTP 403 by default or that no endpoint writes the list: the check is off by default, the web UI sets it, and the quoted refusal text is the current one. `changelog.d/README.md` gains a "Breaking or not" test with examples from this review, `AGENTS.md` points to it, and `/commit` and `/submit-pr` ask it of every fragment.
