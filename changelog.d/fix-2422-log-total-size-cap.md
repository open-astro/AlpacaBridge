### Added

- **`logging.max_total_size_mb` caps all log files together, across days** (AlpacaHTTP, issue #2422): default 1024 MiB (about 34 h of TRACE on an iOptron rig, which logs about 30 MiB an hour), env `ALPACAHTTP_LOG_MAX_TOTAL_SIZE_MB`, `0` = no total cap; a negative or unparsable value keeps the yaml/default value. Over the cap the oldest files are deleted first: the oldest date first and, within a date, its highest part first and its current file last. The day being written always goes last, even when another file carries a later date (a clock that jumped ahead and came back), so a rotation never deletes the session's own parts first. A night that crosses midnight is no longer cut at a per-day limit, so the next afternoon last night is still on disk, after midnight included. The file being written is counted but never deleted. The cap is checked after every rotation, at midnight and at start-up (with `max_file_size_mb: 0` there is no rotation, so only the last two). Start-up warns when the total cap is smaller than the per-file cap. File names are unchanged (`alpacabridge-YYYY-MM-DD[.N].log`, uncompressed), so the web viewer and Ara's bug report read them as before. `docs/troubleshooting.md` now says how to switch to TRACE for one session and back, and how to raise the cap on a package install. Covered by `test_log_size_cap.cpp`.

### Changed

- **A day keeps up to 999 rotated log parts instead of 19** (AlpacaHTTP, issue #2422): at the 5 MiB default the 19-part limit kept about 100 MiB a day, which at TRACE on an iOptron rig is about 3 h, so the evening before was gone by morning. Parts now go up to `alpacabridge-YYYY-MM-DD.999.log` (the viewer and `/management/v1/logfiles` accept `.1` to `.999`), and the total size cap above is the limit that applies in practice. A rotation renames only the parts up to the first missing number. Worst-case disk use is now min(`max_total_size_mb` + one `max_file_size_mb`, `max_file_size_mb` × 1000 × `retention_days`) instead of 100 MiB × `retention_days`, because the file being written grows between checks; with `max_file_size_mb: 0` that file can grow past the total cap until midnight. With the 1024 MiB default, a rig that logs more than about 11 MiB a day now loses its oldest files to the size cap before `retention_days` (90) is reached; set `max_total_size_mb: 0` to keep age-only retention.
