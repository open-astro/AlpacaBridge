### Fixed
- **A bare cable pull on a ZWO camera now loses the link**, ZWO camera driver, issue #1667. ASI SDK 1.41 answers a pulled camera with a generic error (`ASI_ERROR_GENERAL_ERROR`, error 1280), a failed exposure status or even success, never a removal code, so `Connected` stayed true and an exposure spent its retries before failing with error 1280. Now a camera call that fails with a generic error, an exposure status of failed, or a temperature read the SDK cannot answer asks the SDK whether the camera is still in its list of connected cameras; when it is not, `Connected` reads false, members throw `NotConnected` with "ZWO camera <serial> was removed from USB; Connect again when it is back", and the exposure fails at once with no retry. A call that succeeds is not checked, so a pull while the camera is idle is found by the next call that fails. The `CameraState` or `ImageArray` read that finds the loss answers `NotConnected`, as `ImageReady` already did, instead of Idle or the exposure's error. A client Connect after the replug reopens the same camera by serial, as for a removal code. Checked on a rig on 2026-11-03 (ASI2600MM Pro on a CM4, ASI SDK 1.41): a pull during an exposure and an idle pull followed by an exposure each dropped the link within a second of the failed status, and an ASI120MM Mini open and mid-exposure beside it was unaffected (tests "the CameraState read that finds a bare cable pull answers NotConnected", "the ImageArray read that finds a bare cable pull answers NotConnected", "a bare cable pull during an exposure loses the link at the failed status", "a bare cable pull on an idle camera is found by the next temperature read", "a bare cable pull during the image download loses the link", "a generic SDK error on a camera that still enumerates keeps the link").
- **The ZWO dew heater switch reads `Connected` false when its camera is lost**, ZWO dew heater switch, issue #1667. The switch kept `Connected` true and answered `NotConnected` after its camera was removed, a state decision 0009 does not define. Its next heater read or write after the loss now drops its own link: `Connected` false, `DeviceState` empty, members `NotConnected` with the loss reason, which `get_link_fault()` also reports until the next Connect or Disconnect; a Disconnect completes and a Connect after the replug opens the camera afresh (tests "a camera loss reads Connected false on the switch", "a bare cable pull met by the switch drops the switch and the camera", "a heater write that meets a bare cable pull drops the switch").

### Added (tests)
- **ZWO shared open table enumeration check cases**, issue #1667: a generic failure or a failed result on an id the SDK no longer lists retires the open, one on a listed id or a check that cannot run keeps it, only a generic failure asks, and the unlocked download is checked too (five `[zwo][link]` cases in `test_zwo_shared_open_table.cpp`). `FakeZWOSDK::pulled` models the bare pull.
