### Added
- **remotealpaca: SafetyMonitor of an upstream Alpaca server** (AlpacaCore, AlpacaHTTP, web UI, issue #1753): the "Remote Alpaca" vendor now also serves the SafetyMonitor device of another Alpaca server as a device of this server, with the same four settings (upstream host, port, device number, poll period) and the same Connect, snapshot and link rules as the ObservingConditions device. `IsSafe` answers from the poll's snapshot. While the link is lost, `IsSafe` returns `false` and does not throw, so a lost link never reads safe. The link is lost at once when the upstream refuses the connection, otherwise when no poll has had an answer for `max(30 s, 3 x poll period)`; until then `IsSafe` serves the last answer, which can be `true`, and while the link is faulted (three failed polls in a row) it throws `DriverException`. Never connected, connecting, disconnected by the client, or after a Connect that failed, it throws `NotConnected`. A lost link's `DeviceState` is the empty list even when its own `IsSafe` read is the one that finds the loss (the SafetyMonitor base checks `Connected` again after `IsSafe`). The web form's Device Type list gains Safety Monitor. Built under `ALPACACORE_ENABLE_REMOTEALPACA`; fake evidence only, ConformU against the simulators is a rig step.

### Changed
- **remotealpaca: one shared proxy for every device type** (AlpacaCore, issue #1753): what every proxied device shares (the self-loop check, the forwarded Connect and Disconnect, the branded Name and the Description, the `util::PolledState` frame with the link's fault and loss, the command slot and the pass-through of upstream errors) moved out of the ObservingConditions driver into `UpstreamProxy` (`upstream_proxy.h`), and both device types take one config, `RemoteDeviceConfig`. The ObservingConditions behaviour and its tests are unchanged.

### Added (tests)
