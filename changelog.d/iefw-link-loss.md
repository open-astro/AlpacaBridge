### Fixed

- **An iOptron iEFW filter wheel whose USB cable is pulled reads Connected false at once and reconnects with one Connect**, iOptron iEFW filter wheel driver, issue #1723, decision 0009 rule 2. A hangup on a reply read used to throw a `DriverException` "iEFW serial link lost (errno N)", and `EIO`/`ENXIO`/`ENODEV` on a command write a `DriverException` "Write failed", while `Connected` stayed true and the dead port stayed claimed; a hangup while waiting for a move ack was taken for a silent firmware and the move reported success, and the third failed `Position` read in a row reported "communications compromised". The wrapper now releases the port at once, `Connected` reads false, every device operation throws `NotConnected` (a cached `Position` is not served; the config-held names and focus offsets stay readable), `DeviceState` is empty, the web UI firmware is hidden, and `get_link_fault()` gives the loss reason until the next Connect or Disconnect. Nothing reopens the port until the client's next Connect, which reopens it without a Disconnect first, clears a move in progress before the loss and polls the wheel afresh. A cable pulled during the connect, the firmware and stored-offset reads included, fails that Connect with `NotConnected` and keeps no loss reason. A wheel that stops answering with the cable in still latches the "communications compromised" fault with `Connected` true, and `get_link_fault()` now gives that fault text too. While that fault is latched a move is now refused with the same `DriverException` and sends nothing; before, `:WM` went out and, with no ack, the move reported success on a wheel whose `Position` could not be read. A fault that stands for 30 s (`util::kLinkStalenessBound`, on the driver's task clock) is now a lost link, found by the next failed `Position` read or refused move: `Connected` false and the port released as for a pulled cable. The status cache shared by the ZWO, Player One, ToupTek and iEFW drivers gains a read-only `fault_stale()` and stamps its latch on its clock; only the iEFW calls it. No loss time is stamped (no #521 motion-on-relink consumer). Calls on a pulled wheel already failed before this change, so nothing that worked stops working; the refused move and the 30 s loss only affect a wheel whose `Position` reads already fail, where a client could not see a move arrive. Tests: thirteen `iEFW Link - ...` cases in `AlpacaCore/tests/test_ioptron_filterwheel.cpp` (the four fault cases on a fake task clock) and a `fault_stale()` case in `AlpacaCore/tests/test_ttl_status_cache.cpp`. Pty fake evidence only; not checked on the rig.
