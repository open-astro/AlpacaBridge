### Fixed

- **An iOptron iEFW filter wheel whose USB cable is pulled reads Connected false at once and reconnects with one Connect**, iOptron iEFW filter wheel driver, issue #1723, decision 0009 rule 2. A hangup on a reply read used to throw a `DriverException` "iEFW serial link lost (errno N)", and `EIO`/`ENXIO`/`ENODEV` on a command write a `DriverException` "Write failed", while `Connected` stayed true and the dead port stayed claimed; a hangup while waiting for a move ack was taken for a silent firmware and the move reported success, and the third failed `Position` read in a row reported "communications compromised". The wrapper now releases the port at once, `Connected` reads false, every member throws `NotConnected` (a cached `Position` is not served), `DeviceState` is empty, the web UI firmware is hidden, and `get_link_fault()` gives the loss reason until the next Connect or Disconnect. Nothing reopens the port until the client's next Connect, which reopens it without a Disconnect first, clears a move in progress before the loss and polls the wheel afresh. A cable pulled during the connect, the firmware and stored-offset reads included, fails that Connect with `NotConnected` and keeps no loss reason. A wheel that stops answering with the cable in still latches the "communications compromised" fault with `Connected` true, and `get_link_fault()` now gives that fault text too. No loss time is stamped (no #521 motion-on-relink consumer). Calls on a pulled wheel already failed before this change, so nothing that worked stops working. Tests: nine `iEFW Link - ...` cases in `AlpacaCore/tests/test_ioptron_filterwheel.cpp`. Pty fake evidence only; not checked on the rig.
