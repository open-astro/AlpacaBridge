### Fixed

- **Cameras no longer report made-up electrons per ADU, full well or sensor name** (AlpacaCore camera drivers, issue #1277): `ElectronsPerADU` and `FullWellCapacity` now raise `PropertyNotImplemented` on ZWO, ToupTek (and Altair), SVBONY and gphoto cameras, and `FullWellCapacity` does on Player One, instead of answering 1.0, 0.0, the ADU saturation or ZWO's one static figure that does not follow gain; `NotConnected` comes first while disconnected. Player One keeps its real per-gain `POA_EGAIN` read for `ElectronsPerADU` and raises `PropertyNotImplemented` when the camera lacks it or the read fails, instead of returning 1.0. An unknown `SensorName` is now the empty string (ASCOM: "must return an empty string if the name is not known") on ZWO, ToupTek, Altair, SVBONY, Player One, gphoto and QHY, not a "<vendor> Sensor" placeholder. Covered by the `... are not implemented, SensorName has no placeholder` and `an unknown SensorName is empty` cases in `test_zwo_camera.cpp`, `test_touptek_camera.cpp`, `test_svbony_camera.cpp` and `test_playerone_camera.cpp`, the `ElectronsPerADU is the POA_EGAIN read` case in `test_playerone_camera.cpp`, `test_gphoto_fake_sdk.cpp`, `test_altair_camera.cpp` / `test_gphoto_camera.cpp` for the empty name, and the `SensorName is empty when chip info is unreadable` case in `test_qhy_camera.cpp`. Clients that read these values must handle the error; most already do for QHY.

### Added

- **iOptron and Celestron mounts report whether their GPS has a fix** (AlpacaCore telescope drivers, issue #1277): `Action("gps_status")` returns `{"fix":<bool>,"latitude":<deg|null>,"longitude":<deg|null>,"elevation":null}`, with latitude and longitude from the mount's own GPS receiver and `null` unless there is a fix. iOptron reads the `:GLS#` GPS digit (2 = valid GPS data) and the site in the same reply, and lists the action while connected. Celestron reads the GPS module on the AUX bus (linked flag, then latitude and longitude) and lists the action only when the connect found the module. Both throw `NotConnected` while disconnected, and Celestron also stops listing the action once the link is lost (`gps_status is not listed once the link is lost`). On iOptron, `SupportedActions` and `CanAction` read the atomic connected flag without the driver lock, so a `CommandString` exchange in flight does not delay them (`SupportedActions and CanAction do not wait on a held command exchange`). Covered by the `gps_status` cases in `AlpacaCore/tests/test_ioptron_telescope.cpp` and `AlpacaCore/tests/test_celestron_telescope.cpp` (fix, no fix, no GPS module, action listing); not run on a rig. OnStep is not covered.
