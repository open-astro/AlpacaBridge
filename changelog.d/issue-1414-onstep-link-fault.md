### Fixed

- **OnStep: a mount that stops answering while its USB adapter stays plugged in no longer looks connected for ever** (issue #1414, decision 0009): with the mount unpowered or its cable pulled at the mount end, `Connected` stayed true and every position or status read served old values after waiting out the reply timeout. Three failed reads in a row now latch a fault: reads and commands throw "communications compromised" (AbortSlew still sends its stop first) and the link fault says the mount is not answering, while `Connected` stays true; one good reply clears it. A fault that stands for 30 s is a lost link, as for a pulled adapter: `Connected` reads false, calls fail with `NotConnected`, and the client's next Connect relinks, also for a client that only sends commands. A Park or FindHome the mount stops answering right after now fails instead of reporting success. Tests: `test_onstep_link_loss.cpp` "OnStep link loss - a mount that stops answering latches a fault and a reply clears it", "OnStep link loss - a fault latched on status reads serves no fresh position cache", "OnStep link loss - a lost link during the failed reads is not latched as a fault", "OnStep link loss - declaring a lost link while disconnected records nothing", "OnStep link loss - a fault standing past the staleness bound loses the link", "OnStep link loss - a write refused past the staleness bound loses the link", "OnStep link loss - Slewing reports a latched fault during a MoveAxis", "OnStep link loss - a faulted AbortSlew does not restore tracking later", "OnStep link loss - FindHome fails when the mount goes silent after :hC#" and "OnStep link loss - Park fails when the mount goes silent after its :hP# reply".
