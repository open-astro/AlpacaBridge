### Fixed
- **ToupTek cameras: odd sub-frame or full-frame sizes at bin 2 and above no longer fail** (AlpacaCore, issue #977): the SDK rounds the binned output down to an even size, so an odd NumX or NumY came back one pixel short and, since the 5.0.0 beta, failed ImageReady and ImageArray with "frame is smaller than the requested ROI" (ConformU bin 3 full frame on the SC571CC, 4168 / 3 = 1389 rows; any odd sub-frame at bin 2, 3 or 4). The driver now asks the sensor for the next even output size and crops, so the client gets real pixels wherever the grown span fits at the requested origin; when it does not (an odd full frame, or an odd sub-frame that touches the right or bottom edge of the sensor) the last row or column is filled from its neighbour. A frame shorter than the size the ROI math predicts still fails as malformed. The same change fixes odd NumX sub-frames at bin 1, which failed with `Toupcam_WaitImageV4: E_INVALIDARG` on every earlier release: the driver passed a row pitch one pixel narrower than the frame the SDK delivers, and the SDK rejects that. Verified on a GPCMOS01200KPF and an ATR2600M: odd sub-frames at bin 1 to 4 return the requested size with real pixels, edge-touching odd sub-frames at bin 2 to 4 return the requested size with the edge filled, the ATR2600M bin 3 full frame (2074 x 1389) completes with its last row filled, and ConformU 4.5.1 passes both cameras clean at bin 1 to 4.

### Added (tests)
- **ToupTek odd binned ROI cases** (issue #977): the fake SDK models the even output rounding; cases cover the even-grown sub-frame, the odd NumX at bin 1 stride, the odd full frame at bin 3 with the row and the column fill, and a frame short of the binned contract still failing.
