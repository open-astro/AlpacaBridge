### Changed
- **Celestron telescope moved into the device catalog** (AlpacaCore, AlpacaHTTP): the schema (`celestron_schema.cpp`, every build) and factory (`celestron_catalog.cpp`, only under `ALPACACORE_ENABLE_CELESTRON`) replace the router's register arm, its sanitize branch and its driver include. The vendors-OFF text stays "Celestron support not enabled. Rebuild with -DALPACACORE_ENABLE_CELESTRON=ON", the API still refuses an unknown connection type with "Invalid connection type. Use 'auto', 'serial', or 'network'", an empty serial port with "Serial port path is required" and an empty host with "Host IP address is required", and a saved unknown connection type is still read as `serial` (test `Builtin catalog - Celestron normalize accepts '', auto, serial and network, refuses others from the API`). An unknown or non-string `alignmentMode` is still dropped and reads as `auto` (#860; test `Builtin catalog - Celestron alignmentMode keeps a known value and drops an unknown one (#860)`). The auto-detect factory still constructs without a scan (the scan runs at connect). `GET /management/v1/devicecatalog` now lists the `celestron` telescope descriptor. A saved config keeps its `portPath`/`baudRate` and `host`/`tcpPort` whatever its connection type, and an out-of-range `siteLatitude` or `siteLongitude` sent through the API is now refused with the catalog's "siteLongitude is out of range (min -180) (max 180)" text (test `Builtin catalog - Celestron site range is per-field`). `scripts/check_layering.py`'s AlpacaHTTP vendor-include baseline drops from 31 to 30. A saved Celestron config with a wrong-typed `mountIndex`, `baudRate` or similar field no longer fails registration with the #388 `AlpacaException`: the catalog's "has the wrong type" rule erases the field and registration continues, as for the other catalog vendors.
