### Fixed
- **HTTP server and discovery: `http_port: 0` keeps its port and is advertised correctly, and the discovery responder follows protocol v1** (AlpacaHTTP, issue #562, also #564): with `http_port: 0` the server now resolves the OS-assigned port once after the first bind, the descriptor-loss recovery re-binds that port instead of taking a new ephemeral one (a failed re-bind fails recovery as for a fixed port), and the startup log prints it instead of 0. `Discovery` advertises a port set through the new `set_advertised_port()` (it starts at the configured `http_port`), does not answer while that port is 0, and logs the port it sent; the example server hands over `bound_port()` once the listener is up. A probe is answered only when the datagram is exactly `alpacadiscovery1`, optionally followed by CR, LF, NUL or space; a datagram that only contains the text gets no reply. The discovery socket also sets `SO_REUSEPORT` where the platform has it, so it can share UDP 32227 with another Alpaca process that sets only that option, a failed socket option is logged as a warning, and a failed bind now logs the port, the error and that discovery is disabled. `Server::bound_port()` is documented as not authoritative from another thread. Tests: `test_server_socket` closes the listener behind an `http_port: 0` server and requires the rebind to come back on the same port, and `test_discovery` now sends real probes: the exact request, four near-miss datagrams, trailing CR/LF/NUL/space, an `http_port: 0` server (no reply before the port is set, then the resolved port) and two peer sockets binding 32227 alongside the responder.
