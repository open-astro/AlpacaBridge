### Fixed

- **Bisque: Name, Connected, RightAscension and the other getters no longer wait behind a TheSkyX exchange** (Bisque, issue #1438): the whole Bisque telescope driver now exchanges with TheSkyX with the driver state lock free, under the protocol wrapper's per-link lock: connect and handshake (under a transition lock no getter takes), FindHome, Park and its polls, slews and their completion polls, sync, `SetTracking`, MoveAxis, Unpark, SetPark and the position read at the end of sync, slew complete, FindHome and Park. The read takes its snapshot token under the state lock, samples without it and publishes under it, so a read right after sync, slew complete, FindHome or Park still sees the new position. A disconnect clears the driver state and releases the state lock before it closes the link, so Connected answers at once while a PulseGuide reply is still on the wire. Covered by "Bisque snapshot - Name, Connected and RightAscension answer while FindHome runs in TheSkyX", "Bisque snapshot - RightAscension answers while the read at the end of SyncToCoordinates is slow", "Bisque snapshot - Name, Connected and Tracking answer while a SetTracking exchange is slow", "Bisque snapshot - Name and Connected answer while the connect waits on IsParked", "Bisque snapshot - Connected and AtPark answer while a Park polls IsParked", "Bisque snapshot - Connected answers while a disconnect waits for a PulseGuide reply", "Bisque snapshot - RightAscension, Slewing and Connected answer while SlewToCoordinates polls IsSlewComplete", "Bisque snapshot - Connected and Slewing answer while the MoveAxis start exchange is slow", "Bisque snapshot - Connected and Slewing answer while the SlewToCoordinatesAsync command is slow", "Bisque snapshot - Connected and Slewing answer while the Unpark command is slow" and "Bisque snapshot - Connected and Slewing answer while the SetPark command is slow" in `test_bisque_telescope_snapshot.cpp`.
- **Bisque: AbortSlew no longer leaves Slewing true after an initiator's exchange** (Bisque, issue #1438): MoveAxis and both slew forms hold an initiator lock across their gate, command and state write, and AbortSlew holds it across its state clear and command, so the driver state follows the order of the commands on the wire. A SlewToCoordinates whose completion answer arrives as another client retargets no longer clears the Slewing of the retarget. Covered by "Bisque snapshot - AbortSlew during the MoveAxis start exchange leaves Slewing false", "Bisque snapshot - AbortSlew during the SlewToCoordinatesAsync exchange leaves Slewing false" and "Bisque snapshot - a SlewToCoordinates that completes does not clear the Slewing of a retarget" in `test_bisque_telescope_snapshot.cpp`.
